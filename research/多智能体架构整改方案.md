# 多智能体架构整改 / 优化方案

> 对标对象：DeepSeek Harness（`D:\javahouduan\deepseek-harness`）
> 适用范围：javahouduan 平台后端 `houduan/backend` 多智能体子系统
> 技术栈：Spring Boot 3 · Java 17 · MongoDB · GLM API
> 文档性质：正式架构整改方案（阶段四：智能体工程化）

***

## 1. 背景与目标

### 1.1 现状概述

javahouduan 平台已实现一套**手写多智能体协作系统**，位于：

```
houduan/backend/src/main/java/com/edu/backend/agent/
├── BaseAgent.java           # Agent 基础接口
├── AgentRegistry.java       # 注册中心（@PostConstruct 注册）
├── AgentMessageQueue.java   # 消息队列（BlockingQueue，每类型独立通道）
├── SharedKnowledgeBase.java # 共享内存（会话状态/对话历史/Agent共享）
├── TaskDecomposer.java      # 任务分解（关键词规则）
├── CollaborationManager.java# 协作调度（线程池 + Future + 60s 超时）
├── ResultAggregator.java    # 结果聚合
├── PlannerAgent / TutorAgent / AssessorAgent
├── QAAgent / RecommenderAgent / MonitorAgent
├── EMCodeAgent.java         # 编程执行 Agent
└── ProgrammingIntentDetector.java
```

系统现状：**"能跑、结构清晰"**，6+ 类 Agent 已完成 RAG 答疑、教学、评估、推荐等多个教育场景能力。

### 1.2 工程问题（差距清单）

对照 DeepSeek Harness 的工程观，当前实现存在四类关键差距：

| #  | 差距           | 现状                                             | 工程风险           |
| -- | ------------ | ---------------------------------------------- | -------------- |
| G1 | **LLM 不可插拔** | 各 Agent 直接 `@Autowired GlmApiService`（硬编码 GLM） | 换模型需改动所有 Agent |
| G2 | **会话记忆不持久**  | `SharedKnowledgeBase` 用内存 `HashMap`，重启即丢       | 跨设备/重启无法恢复对话   |
| G3 | **注册不可逆**    | `AgentRegistry.register()` 只 `put`，无卸载         | 热插拔/优雅关停不安全    |
| G4 | **执行无守卫管道**  | `CollaborationManager` 直接 `processTask`        | 限流/权限/重试需各处手写  |

### 1.3 对标参考（DeepSeek Harness 的四个工程观）

| 工程观                           | Harness 实现                                  | 对应我们的差距 |
| ----------------------------- | ------------------------------------------- | ------- |
| **能力缝隙 / 万物皆插件**              | `ctx.llm`、`ctx.tools` 等 seam，Provider 可替换   | G1      |
| **事件溯源（Session Log）**         | `SessionEvent` 只追加日志为唯一真相，可重建               | G2      |
| **可逆副作用（Reversible effects）** | 每个注册返回 disposer，卸载自动回滚                      | G3      |
| **守卫执行管道**                    | `pre-execute → execute → post-execute` + 策略 | G4      |

## 2. 整改方案

四项整改，按优先级排序。每项包含：设计、涉及文件、改动点。

***

### 2.1 G1：LLM 能力缝隙化（最高优先级）

#### 设计目标

让所有 Agent 通过一个**统一的** **`ChatProvider`** **接口**与大模型交互，实现模型可插拔：

- 现有 GLM 作为默认 Provider

- 预留 DeepSeek Provider 入口（与本次新增的 deepseek-harness 呼应）

- Agent 与具体模型解耦，切换零代码改动

#### 接口设计

```java
public interface ChatProvider {
    String providerName();                                 // 如 "glm-4"、"deepseek"
    boolean supportsMultiModal();                          // 是否支持多模态
    String chat(String systemPrompt, List<Map<String,Object>> messages, Map<String,Object> params);
    // 增加承载返回引用/工具调用的扩展：
    default boolean supportsCitations() { return false; }
}
```

#### 实现拆分

1. **定义接口** `ChatProvider`（新建 `agent/llm/ChatProvider.java`）
2. **重构现有** `GlmApiService` → 实现 `ChatProvider`，方法重命名为 `chat(...)` 统一签名
3. **新建** `DeepSeekChatProvider`（预留，本次可只建桩，指向 future/module）
4. **Agent 改造**：6 类 Agent 的 `@Autowired GlmApiService` → `List<ChatProvider>` + 按名选择（或 `@Qualifier` 指定默认）
5. **配置化路由**：`application.yml` 增加 `agent.llm.provider=glm`，启动时注入对应实现

#### 涉及文件

| 文件                                                        | 动作                              |
| --------------------------------------------------------- | ------------------------------- |
| `agent/llm/ChatProvider.java`                             | 新建                              |
| `agent/llm/GlmChatProvider.java`                          | 由 `service/GlmApiService` 迁移/包装 |
| `agent/llm/DeepSeekChatProvider.java`                     | 新建（桩）                           |
| `Planner/Tutor/Assessor/QA/Recommender/MonitorAgent.java` | 改为依赖 `ChatProvider`             |
| `application.yml`                                         | 增加 `agent.llm.provider` 配置项     |

#### 验收标准

- 切换 `agent.llm.provider` 配置即可换模型，Agent 源码零改动

- 原有 GLM 能力行为完全不变（回归测试通过）

### 2.2 G2：会话记忆事件溯源化 + 持久化（高优先级）

#### 设计目标

把 `SharedKnowledgeBase` 从**内存 HashMap** 升级为**只追加事件日志（append-only log）作为唯一真相**，并持久化到 MongoDB：

- 模型可自讨论中重建的一切，都必须能从日志重建

- 服务重启、多设备、前端刷新均可恢复完整对话

#### 事件模型

```java
public enum SessionEventType {
    USER_MESSAGE,      // 用户发言
    ASSISTANT_MESSAGE, // Agent 回复
    TOOL_CALL,         // 工具/检索调用
    TURN_START, TURN_END, // 一轮开始/结束
    SYSTEM_NOTE        // 系统备注
}

public class SessionEvent {
    String sessionId;
    SessionEventType type;
    String role;         // user / assistant
    String content;
    String agentType;    // 产生该事件的 Agent
    String sourceMaterial; // 引用来源（配合 RAG 引用）
    Float score;         // 相似度（optional）
    long timestamp;
    String eventId;      // UUID
}
```

#### 持久化设计

- 新增 MongoDB 集合 `session_events`

- **写入**：`append(SessionEvent)` 幂等追加（按 `eventId` 判重）

- **读取**：`deriveMessages(sessionId)` 从日志重建 `[{role, content}, ...]`

- **裁剪**：`truncate(sessionId, keepLastN)` 保留近 N 个事件，遵循"总 token < 3000"的项目约束

#### 与现有代码关系

`SharedKnowledgeBase.conversationHistory` → 由 `SessionEventStore`（新类）替代为日志派生，其余内存字段逐步迁移。

#### 涉及文件

| 文件                                     | 动作                               |
| -------------------------------------- | -------------------------------- |
| `agent/session/SessionEventType.java`  | 新建                               |
| `agent/session/SessionEvent.java`      | 新建                               |
| `agent/session/SessionEventStore.java` | 新建（MongoTemplate 实现）             |
| `agent/SharedKnowledgeBase.java`       | 改造：历史读写委托 `SessionEventStore`    |
| `agent/CollaborationManager.java`      | `addConversationEntry` 调用处改走事件日志 |
| `entity/`                              | 视需要新增 `SessionEventDocument` 实体  |

#### 验收标准

- 服务重启后，`getConversationHistory(sessionId)` 能从 MongoDB 恢复

- 对话日志为只追加（无覆盖写），`eventId` 防重

- token 裁剪逻辑满足平台约束

### 2.3 G3：注册中心支持可逆卸载（中优先级）

#### 设计目标

`AgentRegistry.register()` 返回一个 **disposer（卸载函数）**，使注册成为"可逆效应"：

- 运行时热插拔某类 Agent

- 优雅关停单个 Agent（先停止接收消息，再清理）

#### 改动点

```java
// 现在：void register(AgentType, BaseAgent)
// 改为：返回 disposer
public Runnable register(AgentType type, BaseAgent agent) {
    agentPool.computeIfAbsent(type, k -> new CopyOnWriteArrayList<>()).add(agent);
    return () -> {
        agentPool.get(type).remove(agent);   // 1. 摘除路由
        messageQueue.clearReceiver(type, agent.getId()); // 2. 清理该实例的入队消息
        agent.onUnload();                    // 3. 调用 Agent 自身的卸载钩子
    };
}
```

#### 涉及文件

| 文件                             | 动作                       |
| ------------------------------ | ------------------------ |
| `agent/AgentRegistry.java`     | `register` 返回 `Runnable` |
| `agent/AgentMessageQueue.java` | 增加 `clearReceiver`       |
| `agent/BaseAgent.java`         | 增加默认空实现 `onUnload()`     |

#### 验收标准

- `register` 返回值可 `run()` 完成任务卸载

- 卸载后该实例不再被分配新任务，已占用的队列消息被清理

### 2.4 G4：执行守卫管道（中优先级）

#### 设计目标

在 `CollaborationManager` 的任务执行前后增加**统一策略钩子**，而非各处手写：

- `preExecute(task)`：权限检查、限流、token 预算、模型路由

- `postExecute(result)`：结果记录、失败重试决策、引用溯源

#### 改动点

```java
// CollaborationManager.processTask(agent, task) 重构为：
public AgentResult processTask(BaseAgent agent, Task task, TaskPolicy policy) {
    beforeExecute(agent, task, policy);        // pre-execute 钩子
    if (policy.isTimeoutBudgetExceeded(task)) { reject(...); }
    AgentResult result;
    try {
        result = agent.processTask(task);
        return afterExecuteSuccess(result, policy);
    } catch (Exception e) {
        return afterExecuteFailure(e, policy); // 内含按 policy 的重试
    }
}
```

#### 涉及文件

| 文件                                  | 动作                              |
| ----------------------------------- | ------------------------------- |
| `agent/CollaborationManager.java`   | 拆分 `beforeExecute/afterExecute` |
| `agent/TaskPolicy.java`             | 新建（限流/超时预算/重试次数）                |
| `agent/agent/ResultAggregator.java` | 复用 `postExecute` 的失败重试逻辑        |

#### 验收标准

- 限流/超时/重试逻辑集中在一个 `TaskPolicy`，可编排

- 现有 60s Future 超时逻辑迁移至 `TaskPolicy` 统一管理

## 3. 分阶段实施计划

| 阶段 | 内容                               | 耗时  | 依赖              |
| -- | -------------------------------- | --- | --------------- |
| P1 | G1 LLM 缝隙化（接口 + GLM 适配 + 配置路由）   | 重点  | 无               |
| P2 | G2 会话事件溯源 + MongoDB 持久化          | 重点  | P1（Provider 引用） |
| P3 | G3 可逆注册 + G4 守卫管道                | 次重点 | 无               |
| P4 | 回归测试 + `ChunkSync`/`BM25` 与新管道对齐 | 收尾  | P1–P3           |

> 说明：P1 与 P3 相互独立，可并行；P2 依赖 P1 的 Provider 抽象；P4 为全量回归。

## 4. 明确不做（防过度设计）

| 不采纳项                 | 原因                                               |
| -------------------- | ------------------------------------------------ |
| 引入 Cordis / 插件框架本体   | 它是 TS/Node 生态，与 Spring Boot 跨语言成本过高              |
| 微服务化拆分上百个包           | 当前规模（几百\~上千 chunk，数十 Agent）用不到                   |
| 5 种派发模式全量枚举          | 只需 `NOTIFY→emit`、`QUERY→serial`、协作→`parallel` 即可 |
| 基于 Milvus/Neo4j 的重排序 | 规模不足以支撑复杂度，BM25+RRF 已够（见既有优化）                    |
